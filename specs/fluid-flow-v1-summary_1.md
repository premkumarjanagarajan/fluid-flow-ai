# Fluid Flow v1.0 — Summary for Claude Code

## Purpose

This document summarizes what v1.0 adds on top of Fluid Flow Core v0.9. Feed this to Claude Code along with the full spec (`fluid-flow-v1-spec.md`), the v0.9 repo, and the domain-catalog.yaml to produce documentation in Fluid Flow's existing style.

---

## What v0.9 Already Has (Do Not Change)

- **Orchestrator** — staged lifecycle (Stages 0-6) with triage, shell detection, workspace detection, RE, workflow selection, initiative creation, workflow routing, completion
- **Knowledge-base-core** — tiered loading manifest (always-load vs conditional), KB compliance subagent at phase boundaries
- **Primitives** — human-gate (A/B/C after every step), state-manager, analytics, kb-compliance
- **Pluggable workflows** — `workflow/{name}/wf-{name}.md` with frontmatter, phase/step chains, per-workflow knowledge-core
- **Skills** — shell-detection, reverse-engineering (with per-repo subagents), branch-creation
- **Initiatives** — typed folders (`feature/`, `fix/`, `chore/`), metadata (state.md, audit.md, analytics.md)
- **Entry points** — `.cursor/rules/instructions.mdc`, `.github/copilot-instructions.md`

All of this is preserved. v1.0 is additive.

---

## What v1.0 Adds

### 1. Fluid Flow Workspace

A dedicated repo per bounded context. Replaces per-repo copies of Fluid Flow. Contains the framework, all initiatives, combined RE artifacts, ff-workspace.yaml, and the .code-workspace file. No application code. Repo naming: `{context}-ff-workspace`.

### 2. ff-workspace.yaml (Generated by RE)

NOT manually maintained. Generated by the RE skill from discovered state. Contains: repos (name, path, type, language, team, description), teams (name, Slack), governance flags, shared repo metadata. Shared repo discovery via GitHub MCP.

Human-edited fields (change_coordination, team Slack channels, governance flags) are preserved across RE regeneration. Everything else is refreshed from code reality.

### 3. Workspace Setup (New Triage Intent)

Fourth triage intent added to the orchestrator. When multiple repos detected without ff-workspace.yaml, presents a prompt explaining Fluid Flow Workspace advantages and offers A) Set up / B) Continue single-repo. If A: runs workspace setup skill (RE across all repos → generate combined architecture → generate ff-workspace.yaml → GitHub MCP shared repo discovery → human review).

### 4. Cross-Repo RE with Combined Architecture

Per-repo artifacts stay in each repo at `{repo}/reverse-engineering/` (unchanged v0.9 behaviour). A post-RE subagent reads per-repo artifacts and produces two combined workspace-level files:
- `reverse-engineering/combined-architecture.md` — all repos and their relationships
- `reverse-engineering/combined-c4.md` — C4 where containers = repos

Plus `reverse-engineering/incident-learnings.md` (production feedback, not generated by RE, manually or CI-updated).

### 5. Conflict Detection (New Skill)

`skills/conflict-detection/conflict-detection.md`. Runs after planning produces target-repos.md. Reads ff-workspace.yaml, combined-architecture.md, and active initiative target-repos.md files. Severity: BLOCKING, HIGH, MEDIUM, CROSS-CONTEXT, LOW. CROSS-CONTEXT triggers mandatory human acknowledgement for shared repos.

### 6. Lazy Branching

Workspace branched at Stage 4 (initiative creation). Target repos branched at construction start, after plan and conflict detection. Same branch name across all repos. Stage 6 completion creates PRs per repo in dependency order.

### 7. Initiative Workflow (New Pluggable Workflow)

`workflow/initiative/wf-initiative.md`. Five phases: Scope (domain catalog → domain impact), Decompose (per-workspace scope), Contracts (cross-workspace schemas), Sequence (dependency order), Seed (per-workspace spec stubs). Does not produce code. AI proposes affected domains; human validates. AI cannot negotiate priorities, resolve resource conflicts, or decide deployment timing.

### 8. Shared Repo Handling

Three progressive strategies per repo via `change_coordination` field in ff-workspace.yaml:
- `manual` (current) — human checks with other workspaces
- `index` (future) — global active-specs index repo
- `workspace` (future) — dedicated workspace for contended shared repos

## Orchestrator Changes (4 Additions)

1. **Triage**: Add Workspace Setup intent. Multi-repo detection prompt when no ff-workspace.yaml found.
2. **Stage 1**: After workspace scan, check for ff-workspace.yaml. Store WORKSPACE_NAME and REPO_LIST.
3. **Stage 2**: Dual RE output — per-repo (unchanged) + combined architecture in workspace.
4. **Stage 5**: After planning, if target-repos.md exists → conflict detection → human-gate → lazy branching.

Everything else unchanged.

## Known Limitations (March 2026)

| Issue | Workaround |
|-------|------------|
| `.github/` not auto-discovered in multi-root (vscode#296972) | Explicit path mappings in `.code-workspace` |
| `AGENTS.md` unreliable in multi-root (community#183510) | Use `.cursor/rules/` and explicit copilot-instructions paths |
| Copilot Coding Agent single-repo only (vscode#259829) | Local agent mode for orchestrator, cloud per-repo |
| `copilot-instructions.md` not loaded in multi-root (vscode#264837) | Use `.instructions.md` with `applyTo` patterns |

## Rebranding Instructions for Claude Code

1. Follow v0.9 conventions: README structure, Mermaid diagrams, table formats, section hierarchy, display banners
2. Use v0.9 terminology: orchestrator, knowledge-base-core, primitives, skills, initiatives, phases, steps
3. Present v1.0 as an extension of v0.9, not a replacement
4. New workflow uses same `wf-{name}.md` + phase/step structure
5. New skills follow the pattern established by shell-detection and reverse-engineering
6. ff-workspace.yaml is a generated artifact, not a manually-maintained config — emphasise this distinction
7. Maintain governance-first tone — human-gate after every step, kb-compliance at phase boundaries
8. The domain catalog is an external input, not a Fluid Flow artifact
9. "Fluid Flow Workspace" is the branded term for the multi-repo setup — use it consistently
10. The three-tier model (Initiative → Workspace → Repo) is a scope expansion, not a new architecture
