# Fluid Flow v1.0 — Fluid Flow Workspace

## Spec Metadata

- **Branched from**: Fluid Flow Core v0.9
- **Status**: Draft
- **Date**: 2026-03-15

---

## 1. What This Spec Adds

Fluid Flow v0.9 is a well-structured, single-repo orchestration framework. v1.0 extends it to operate across **Fluid Flow Workspaces** — multiple repositories orchestrated through a dedicated workspace repo.

Everything in v0.9 is preserved: the orchestrator lifecycle, knowledge-base-core with tiered loading and KB compliance subagents, pluggable workflows, primitives (human-gate, state-manager, analytics, kb-compliance), skills, and the initiative folder structure. Nothing is replaced.

v1.0 adds:

| Capability | What it does |
|------------|-------------|
| **Fluid Flow Workspace** | A dedicated repo per bounded context that hosts Fluid Flow, all initiative artifacts, and the workspace file |
| **ff-workspace.yaml** | Auto-generated workspace composition file — repos, teams, governance, shared repo flags |
| **Workspace Setup** | New triage intent that bootstraps a Fluid Flow Workspace from a multi-root VS Code workspace |
| **Cross-Repo RE with Combined Architecture** | Per-repo RE artifacts written to each repo + combined architecture view in the workspace |
| **Conflict Detection** | Pre-construction skill comparing active initiatives for contract and file conflicts |
| **Lazy Branching** | Workspace repo branched at inception; target repos branched only at construction |
| **Initiative Workflow** | New pluggable workflow for cross-workspace initiatives using the org-level domain catalog |
| **Incident Learnings** | New RE artifact capturing production feedback for agent context |

### 2.3 What Moves to the Fluid Flow Workspace

| What | From (v0.9 per-repo) | To (v1.0 workspace) |

Individual repos retain their own `reverse-engineering/` artifacts (per-repo detail). The workspace adds combined architecture views on top.

## 3. Workspace Setup

### 3.1 New Triage Intent

v0.9 triage has three intents: Question, Continue, New. v1.0 adds a fourth.

| Intent | Criteria | Action |
|--------|----------|--------|
| **Question** | No development needed | Answer directly |
| **Continue** | Matches existing incomplete initiative | Resume from last stage |
| **New** | Development request, matching initiative not found | Run Stages 0-6 |
| **Workspace Setup** | No `ff-workspace.yaml` found AND workspace has multiple repos, OR user explicitly requests workspace setup | Run workspace setup skill |

### 3.2 Multi-Repo Detection Prompt

When the orchestrator detects a multi-root workspace with no `ff-workspace.yaml`, before proceeding to Stages 0-6:

```
══════════════════════════════════════════════════════════
  MULTI-REPO WORKSPACE DETECTED
══════════════════════════════════════════════════════════

  This workspace contains {N} repositories.
  Fluid Flow can set this up as a Fluid Flow Workspace,
  which gives you:

  • Unified codebase awareness — the AI sees architecture,
    dependencies, and contracts across all {N} repos
  • Cross-repo initiative specs — plan features that span
    multiple repos in a single specification
  • Conflict detection — catch contract and file conflicts
    between parallel initiatives before construction
  • Single version of Fluid Flow — no copies in each repo,
    one source of truth for workflows and governance

  A) Set up as Fluid Flow Workspace (recommended)
  B) Continue with single-repo mode

══════════════════════════════════════════════════════════
```

If the user selects **B**, the orchestrator proceeds with v0.9 single-repo behaviour. No disruption to existing users.

If the user selects **A**, the orchestrator loads `skills/workspace-setup/workspace-setup.md`.

### 3.3 Workspace Setup Skill

**Location**: `skills/workspace-setup/workspace-setup.md`

**Flow**:

1. **Read `.code-workspace`** — extract the repo list from the `folders` array
2. **Shell detection** — same as Stage 0
3. **Run RE across all repos** — uses existing `skills/reverse-engineering/reverse-engineering.md` with subagents per repo
   - Per-repo artifacts written to `{repo}/reverse-engineering/` (inside each repo)
   - Combined architecture artifacts written to `reverse-engineering/` in the workspace repo
4. **Generate `ff-workspace.yaml`** from RE findings:
   - Repos: name, path, type, language(s), team (from CODEOWNERS or GitHub API), description (from RE business-overview)
   - Governance: default flags based on knowledge-base-core (ISO 27001 if security KB exists, etc.)
5. **Discover shared repos via GitHub MCP**:
   - For each repo in the workspace, query: "which other repos in org `BetssonGroup` contain a `.code-workspace` file or `ff-workspace.yaml` that references this repo?"
   - If found: add `shared: true`, `also_in: [list]`, `change_coordination: manual` to the repo entry
   - If GitHub MCP is not available: skip this step, shared repos can be flagged manually later
6. **Present `ff-workspace.yaml`** to the human for review via human-gate
7. **Done** — workspace is ready. Future requests route through normal Stages 0-6

|-------|--------|---------------------------|

| change_coordination | Human decision | No (preserved across regeneration) |
| teams (slack channels) | Human or org API | No (preserved) |
| governance flags | Defaults from KB presence | No (preserved after first review) |

## 4. Cross-Repo Reverse Engineering

### 4.1 Changes from v0.9

v0.9 RE already scans all repos in the workspace with parallel subagents per repo. The skill, subagent strategy, templates, and parallel execution are unchanged.

v1.0 adds:

1. **Dual output**: Per-repo artifacts stay in each repo at `{repo}/reverse-engineering/`. Combined workspace-level artifacts are written to `reverse-engineering/` in the Fluid Flow Workspace.
2. **Combined architecture**: A post-RE step reads per-repo architecture and dependency artifacts and produces workspace-level views.
3. **ff-workspace.yaml generation**: RE generates the workspace composition file from its findings (Section 3.4).
4. **Manifest validation**: On incremental RE updates, compare discovered state against `ff-workspace.yaml` and propose updates if repos have changed.

### 4.2 Per-Repo Artifacts (unchanged from v0.9)

Written to `{repo}/reverse-engineering/` by each subagent. Same 11 artifacts, same templates:

business-overview.md, architecture.md, c4-architecture.md, code-structure.md, api-documentation.md, component-inventory.md, technology-stack.md, dependencies.md, code-quality-assessment.md, test-coverage-analysis.md, reverse-engineering-timestamp.md

These remain in each repo so developers working outside the Fluid Flow Workspace still have context.

### 4.3 Combined Workspace Artifacts (new)

Written to `reverse-engineering/` in the Fluid Flow Workspace after all per-repo subagents complete. Produced by a post-RE subagent that reads the per-repo artifacts and synthesises.

#### combined-architecture.md

System-level architecture showing all repos and their relationships. Shows inter-repo data flows (Kafka topics, REST API calls, shared library dependencies). Each component is attributed to its source repo. Mermaid diagrams show the bounded context as a whole.

This is the primary artifact the orchestrator and conflict detection use for cross-repo awareness. When the agent needs to know "what happens if I change the BetPlacedEvent schema," this file tells it which repos publish and consume that event.

#### combined-c4.md

C4 model where:
- Level 1 (Context): The bounded context as a system, external actors, external systems
- Level 2 (Container): Each repo is a container, showing relationships between them
- Level 3 (Component): Key components within each repo that participate in cross-repo flows
- Level 4: Omitted at workspace level (available in per-repo c4-architecture.md)

#### incident-learnings.md

Not generated by RE. Stored alongside combined artifacts. Updated manually or via CI after post-mortems.

```markdown
# Incident Learnings

**Workspace**: sportsbook
**Last Updated**: {ISO timestamp}

## Active Learnings

### INC-2026-0142: GraphQL overload on sportsbook-api (2026-02-28)

- **Affected repos**: sportsbook-api, sportsbook-events
- **Root cause**: Missing rate limiting on /api/v2/bets batch endpoint
- **Agent guidance**: Any changes to the bet placement flow MUST consider rate limiting. The batch endpoint processes up to 10k requests/second during peak.

### INC-2026-0098: Settlement delay due to schema mismatch (2026-01-15)

- **Affected repos**: sportsbook-events, sportsbook-settlements, shared-contracts
- **Root cause**: Schema updated in sportsbook-events without updating sportsbook-settlements
- **Agent guidance**: When modifying shared Kafka schemas, deploy consumers before producers. Ensure backward compatibility.
```

Entries are pruned when the root cause is fully addressed.

### 4.4 RE Skill Changes

The `skills/reverse-engineering/reverse-engineering.md` needs two additions:

1. **Output path for combined artifacts**: After all per-repo subagents complete, launch one additional subagent to read per-repo `architecture.md`, `dependencies.md`, `c4-architecture.md`, and `api-documentation.md` files, then produce `combined-architecture.md` and `combined-c4.md` in the workspace's `reverse-engineering/` directory.

2. **ff-workspace.yaml generation**: After combined artifacts, generate or update `ff-workspace.yaml` from per-repo RE findings and GitHub MCP queries.

## 5. Conflict Detection

### 5.1 New Skill

**Location**: `skills/conflict-detection/conflict-detection.md`

### 5.2 When to Run

After any workflow's planning phase produces `target-repos.md`, before construction begins. The orchestrator calls this skill at Stage 5 between planning and construction phases.

### 5.3 Algorithm

```
1. Read ff-workspace.yaml for repo list and shared repo flags
2. Read combined-architecture.md for cross-repo relationships
3. Read target-repos.md for the current initiative
4. Scan initiatives/ for all active initiatives (state.md status != Completed)
5. For each active initiative with a target-repos.md:
   a. Same repos targeted? → check for overlapping files/directories
   b. Same data flows modified? → flag from combined-architecture.md
   c. Same APIs modified? → flag from per-repo api-documentation.md
6. Check shared repos (shared: true in ff-workspace.yaml):
   a. Emit CROSS-CONTEXT warning with also_in list
7. Produce initiatives/{name}/artefacts/conflict-report.md
```

### 5.4 Severity

| Severity | Condition | Action |
|----------|-----------|--------|
| BLOCKING | Same schema or API modified by two active initiatives | Must resolve before construction |
| HIGH | Same files targeted in the same repo | Coordinate implementation order |
| MEDIUM | Upstream data flow change affecting downstream active initiative | Notify downstream team |
| CROSS-CONTEXT | Shared repo modified, other workspaces may be affected | Warn developer, require manual check (see Section 6) |
| LOW | Same repo targeted but different areas | Informational only |

### 5.5 Output

`initiatives/{name}/artefacts/conflict-report.md` presented via human-gate. For BLOCKING or CROSS-CONTEXT, the gate MUST NOT be skipped.

## 6. Shared Repos Across Workspaces

Repos appearing in multiple Fluid Flow Workspaces are flagged automatically by GitHub MCP during workspace setup (Section 3.3) or manually.

### 6.1 Option C: Manual Coordination (Current)

When `change_coordination: manual`:

1. Conflict detection emits a `CROSS-CONTEXT` warning
2. Warning includes the `also_in` list from `ff-workspace.yaml`
3. Conflict report includes mandatory acknowledgement:

```markdown
### CROSS-CONTEXT WARNING: shared-contracts

This initiative modifies `shared-contracts`, which is also used by:
- casino-ff-workspace
- rewards-ff-workspace

**Required action**: Check with teams in those workspaces before proceeding.

[ ] Confirmed — no conflicting work in other workspaces
[ ] Conflicting work found — coordination plan: _______________
```

4. Human gate cannot be skipped for shared repo modifications

### 6.2 Option B: Global Active-Specs Index (Future)

When `change_coordination: index`:

A single git repo (`ff-active-index`) where each workspace publishes a summary when an initiative enters construction targeting a shared repo. Conflict detection checks both local initiatives AND the global index.

### 6.3 Option A: Shared Repo Workspace (Future)

When `change_coordination: workspace`:

Heavily-contended shared repos get their own lightweight Fluid Flow Workspace with active initiative tracking. Other workspaces query it via MCP.

### 6.4 Decision Matrix

| Factor | Manual | Index | Workspace |
|--------|--------|-------|-----------|
| Infrastructure | None | One git repo | One repo + MCP per shared repo |
| Conflict detection | Human-verified | Automated cross-workspace | Automated, authoritative |
| When to use | < 1 collision/sprint | Weekly collisions | Daily collisions |

Each shared repo can independently move between strategies. The `change_coordination` field in `ff-workspace.yaml` controls which strategy the conflict detection skill uses per repo. This field is preserved across RE regeneration.

## 7. Initiative Workflow

### 7.1 Purpose

A new pluggable workflow at `workflow/initiative/` for cross-workspace initiatives spanning multiple bounded contexts. Dropped into the orchestrator's workflow selection at Stage 3 like any other workflow.

The initiative workflow does not produce code. It produces the inputs each workspace needs to start its own lifecycle.

### 7.2 Domain Catalog

The initiative workflow's primary input is the **BetssonGroup Domain Catalog** (`domain-catalog.yaml`) — an org-level registry of ~3,200 GitHub repositories across 11 product domains.

The AI reads the domain catalog to **propose which domains and workspaces are involved**. The human validates. The AI can flag domains humans would miss — identifying that `wallet-loyalty-bridge` connects wallet to gamification when planning a cashout feature.

The domain catalog is an existing Betsson artifact used by product agents. It is not owned or maintained by Fluid Flow.

### 7.3 Workflow Definition

```
workflow/initiative/
  wf-initiative.md
  1-scope/
    1-scope/
      1-scope.md
  2-decompose/
    2-decompose/
      2-decompose.md
  3-contracts/
    3-contracts/
      3-contracts.md
  4-sequence/
    4-sequence/
      4-sequence.md
  5-seed/
    5-seed/
      5-seed.md
```

```markdown
## Phases

| Phase | Name | Steps | Goal |
|-------|------|-------|------|
| 1 | Scope | 1 | Domains identified, key repos mapped, integration points found |
| 2 | Decompose | 1 | Per-workspace scope definitions |
| 3 | Contracts | 1 | Cross-workspace contract designs |
| 4 | Sequence | 1 | Workspace dependency order and phase plan |

## Phase Chain

2. Load `2-decompose/2-decompose/2-decompose.md`
3. Load `3-contracts/3-contracts/3-contracts.md`

## Artifacts Location

Step outputs are saved to `initiatives/{INITIATIVE_NAME}/artefacts/` with `{phase}.{step}-` prefix.

## External Inputs

- `domain-catalog.yaml` — org-level domain registry (must be accessible in workspace or provided)
- `ff-workspace.yaml` files from involved workspaces (read via filesystem or GitHub MCP)
```

### 7.4 Scope Step

**Input**: Natural language initiative description

**Process**:
1. Read `domain-catalog.yaml`
2. Analyse initiative against domain descriptions and key repo descriptions
3. For each domain, classify: **Confirmed** (directly required), **Evaluate** (possibly required), **Not affected**
4. Identify cross-domain integration points (repos in multiple domains, event flows)
5. Check if Fluid Flow Workspaces exist for confirmed domains (via GitHub MCP or user input)

**Output**: `artefacts/1.1-domain-impact.md`

```markdown
# Domain Impact Analysis

**Initiative**: Launch cashout for sportsbook
**Date**: {ISO timestamp}

## Confirmed Domains

### Sportsbook
- **Reason**: Cashout is a core sportsbook feature
- **Key repos**: sb-betting-cashout, sb-betting-couponplacement, obg-sportsbook
- **FF Workspace**: sportsbook-ff-workspace (exists)

### Payments
- **Reason**: Cashout requires payout processing
- **Key repos**: payment-paas, payment-psp
- **FF Workspace**: not found

### Wallet
- **Reason**: Cashout requires balance deduction
- **Key repos**: wallet, techsson-wallet-api
- **FF Workspace**: not found

## Evaluate

### Campaigns & Rewards
- **Reason**: Cashout may interact with active bonuses
- **Decision needed**: Does cashout interact with active bonuses?

### Gamification
- **Reason**: wallet-loyalty-bridge connects wallet to gamification
- **Decision needed**: Should cashout trigger loyalty events?

## Cross-Domain Integration Points

| Integration | From | To | Type |
|-------------|------|-----|------|
| Cashout payout request | Sportsbook | Payments | New event/API |
| Balance deduction | Sportsbook | Wallet | Existing wallet API |
| Cashout completion | Payments | Sportsbook | New callback/event |

## Decision Required

[ ] Confirm sportsbook, payments, wallet as in-scope
[ ] Include or exclude campaigns-and-rewards
[ ] Include or exclude gamification
```

### 7.5 Decompose Step

**Input**: Approved domain-impact.md

**Process**: For each confirmed domain, read `ff-workspace.yaml` if it exists (for repo/team detail) or fall back to domain catalog key repos. Break initiative into per-workspace scope — what each workspace builds, consumes, and publishes.

**Output**: `artefacts/2.1-workspace-decomposition.md`

### 7.6 Contracts Step

**Input**: Approved decomposition

**Process**: For each cross-domain integration point, propose contract type (Kafka event, REST API, shared library), draft schema or OpenAPI spec, identify publisher and consumer(s). Check existing per-repo RE artifacts (api-documentation.md, dependencies.md) for reusable contracts.

**Output**: `artefacts/3.1-cross-domain-contracts.md`

### 7.7 Sequence Step

**Input**: Approved contracts

**Process**: Determine dependency order from publish/consume chain. Identify parallelisable work. Propose phased delivery (shared contracts first → publishers → consumers).

**Output**: `artefacts/4.1-delivery-sequence.md`

### 7.8 Seed Step

**Input**: Approved sequence and contracts

**Process**: For each in-scope workspace, generate a spec stub containing: feature description scoped to that workspace, contract responsibilities, dependencies on other workspaces, suggested workflow path (Fast-Track or Comprehensive equivalent).

**Output**: `artefacts/5.1-workspace-stubs/` with one markdown file per workspace

Each stub is designed to be copied into the target workspace's initiatives folder and used as starting input for that workspace's own lifecycle.

### 7.9 What the AI Does vs. What Humans Do

| Activity | AI | Human |
|----------|-----|-------|
| Identify affected domains | Proposes from domain catalog | Validates, adds/removes |
| Identify key repos | Reads catalog and workspace configs | Confirms |
| Identify integration points | Traces flows from catalog and RE artifacts | Validates, adds business rules |
| Decompose per-workspace | Proposes boundaries | Approves, adjusts ownership |
| Design contracts | Drafts schemas | Reviews, approves |
| Determine sequence | Traces publish/consume chain | Adjusts for team capacity |
| Generate spec stubs | Produces from scope + contracts | Distributes to teams |
| Negotiate priorities | **Cannot** | Owns entirely |
| Resolve resource conflicts | **Cannot** | Owns entirely |
| Decide deployment timing | **Cannot** | Owns entirely |

## 9. Lazy Branching

### 9.1 Flow

1. **Stages 0–4**: Branch created in the Fluid Flow Workspace only. Initiative folder created in `initiatives/{type}/{name}/`.
2. **Stage 5, planning phase**: Workflow produces `initiatives/{name}/target-repos.md`.
3. **Stage 5, pre-construction**: Conflict detection skill runs.
4. **Stage 5, construction start**: Create matching feature branches in target repos. Same branch name across all repos.
5. **Stage 5, implementation**: Per-repo execution using workspace access.
6. **Stage 6, completion**: PRs in each target repo + workspace commit.

### 9.2 target-repos.md

Produced by the planning phase of any workspace workflow.

## 10. What Fluid Flow Does NOT Do

These boundaries carry forward from v0.9:

1. **Not a runtime agent framework** — markdown-driven definitions executed by the IDE's native agent infrastructure
2. **Not a dependency graph engine** — `ff-workspace.yaml` is RE-generated, not a live graph database
3. **Not a centralized service** — the Fluid Flow Workspace is a git repo, not a deployed service
4. **Not an agent protocol** — uses MCP and A2A standards if needed
5. **Not a CI/CD system** — creates PRs and risk reports, does not run builds or deployments
6. **Not a replacement for human coordination** — initiative workflow produces artifacts for humans to coordinate with

## 11. Migration from Per-Repo to Fluid Flow Workspace

### 11.1 Steps

1. Identify the bounded context (which repos belong together — ideally 5-8 repos)
2. Create the Fluid Flow Workspace repo (`{context}-ff-workspace`)
3. Copy Fluid Flow v0.9 into the workspace root
4. Create the `.code-workspace` file listing all repos with explicit path mappings
5. Open the workspace in VS Code — the orchestrator detects multiple repos, no `ff-workspace.yaml`, and prompts for workspace setup
6. Workspace setup runs RE, generates `ff-workspace.yaml`, discovers shared repos
7. Move existing initiative folders from individual repos to the workspace
8. Remove `fluid-flow-ai/` from individual repos

### 11.2 Backward Compatibility

Per-repo Fluid Flow instances keep working during migration. The workspace setup prompt offers "Continue with single-repo mode" for teams not ready to adopt. No big bang.

## 12. Known Platform Limitations (March 2026)

| Issue | Impact | Workaround |
|-------|--------|------------|
| `.github/` not auto-discovered in multi-root (vscode#296972) | Agents/instructions invisible | Explicit path mappings in `.code-workspace` |
| `AGENTS.md` unreliable in multi-root (community#183510) | Wrong AGENTS.md loaded | Rely on `.cursor/rules/` and explicit copilot-instructions paths |
| Copilot Coding Agent single-repo only (vscode#259829) | Can't cross-repo in cloud agent | Local agent mode for orchestrator, cloud agent per-repo |
| `copilot-instructions.md` not loaded in multi-root (vscode#264837) | Per-repo conventions ignored | Use `.instructions.md` with `applyTo` patterns |

All workarounds are config — no code or services.

## 14. Open Questions

1. **Workspace granularity**: One FF Workspace per domain (sportsbook, casino, rewards) or per team? Depends on how many repos per context feels manageable.
2. **RE combined artifact size**: Combined architecture across 8 repos may be large. Should the orchestrator load a summary and dive into per-repo detail only when relevant?
3. **Conflict detection integration**: Skill called by orchestrator (current proposal) or a new primitive that runs automatically like kb-compliance?
4. **Domain catalog location**: Where does `domain-catalog.yaml` live? Central repo, or referenced via GitHub MCP?
5. **Shared repo collision rate**: How frequently do cross-workspace collisions occur? Determines if Option C (manual) is sufficient.
6. **Initiative tracking post-seed**: Should there be a `/initiative.track` and `/initiative.validate` phase, or is post-seed coordination entirely manual?
7. **Workspace setup re-run**: When a new repo is added to the `.code-workspace` file, should the orchestrator detect the change and offer to re-run workspace setup incrementally?
